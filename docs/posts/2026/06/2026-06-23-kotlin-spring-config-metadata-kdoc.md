# Why Your KDoc Never Reaches `spring-configuration-metadata.json`

You documented every field of your `@ConfigurationProperties` class with neat
KDoc, yet IntelliJ IDEA shows no autocompletion and no doc tooltips for those
keys. The completions are driven by `META-INF/spring-configuration-metadata.json`,
generated by `spring-boot-configuration-processor` — and on a Kotlin project that
path hides **two independent traps**. This post walks through both, with the
evidence I gathered by actually running kapt and reading the generated artifacts,
plus a check of whether Spring Boot 3.5 changes anything.

<!-- more -->

## TL;DR

1. **The processor never runs** unless it is wired through `kapt` (plain
   `annotationProcessor` is not enough for Kotlin). No kapt — no metadata file at
   all.
2. Even with kapt wired, an **immutable `data class` with `val` constructor
   parameters yields only `groups` and an empty `properties` list** — so there is
   nothing for the KDoc descriptions to attach to. The fix is JavaBean binding
   (`var`).

Both reproduced and fixed empirically. Upgrading to Spring Boot 3.5 does **not**
remove the second trap on its own.

## The symptom

The class is tidy, every field carries KDoc:

```kotlin
@ConfigurationProperties("dema.outbox")
data class OutboxProperties(
    /** Kafka topic events are published to. Required. */
    val topic: String = "",
    /** Scheduler poll interval (ms). */
    val pollIntervalMs: Long = 1000,
    /** Rows fetched per poll. */
    val batchSize: Int = 100,
    /** Event becomes dead (excluded from fetch) after this many failed sends. */
    val maxAttempts: Int = 5,
    val liquibase: Liquibase = Liquibase(),
) {
    data class Liquibase(
        /** Auto-create the outbox_events table on startup. */
        val enabled: Boolean = true,
    )
}
```

In the IDE, the keys under `dema.outbox.*` get neither completion nor doc
popups. The reason is blunt: there is no `spring-configuration-metadata.json` for
the module. IntelliJ reads its hints from exactly that file — no file, no hints.

## The stack

- Kotlin **2.2** (visible in the kapt stub as `@kotlin.Metadata(mv = {2, 2, 0}, …)`)
- Spring Boot **3.4.9** (via the `spring-boot-dependencies` BOM)
- Gradle **9.1.0**, `kapt.use.k2=true`
- The module is a Spring Boot starter; the `kotlin("jvm")` plugin is applied by a
  shared convention build

## Trap #1: the processor is not wired

`spring-boot-configuration-processor` is an ordinary Java annotation processor
(APT). In Kotlin, APT runs only through **kapt**: kapt generates Java stubs from
your `.kt` sources and feeds those stubs to Java processors. Put the processor in
the `annotationProcessor` configuration instead of `kapt`, and it simply will not
process your Kotlin classes.

The affected module's `build.gradle.kts` had neither the kapt plugin nor the
dependency:

```kotlin
description = "Transactional outbox starter (Postgres + Kafka)"

dependencies {
    api("org.springframework.boot:spring-boot-starter-jdbc")
    // … no processor anywhere, neither in kapt nor elsewhere
}
```

A sibling module where metadata *was* being generated declared it explicitly:

```kotlin
plugins {
    kotlin("kapt")
}

dependencies {
    kapt("org.springframework.boot:spring-boot-configuration-processor")
}
```

The shared convention plugin does not add kapt globally, so every module wires
the processor itself. Conclusion for trap #1: the processor never ran, the file
was never produced.

## Trap #2: kapt is wired, but `properties` is empty

Wire kapt, rebuild `:outbox-starter:kaptKotlin` — the file appears. But inside:

```json
{
  "groups": [
    { "name": "dema.outbox",           "type": "org.dema.outbox.OutboxProperties" },
    { "name": "dema.outbox.liquibase", "type": "org.dema.outbox.OutboxProperties$Liquibase",
      "sourceMethod": "getLiquibase()" }
  ],
  "properties": [],
  "hints": []
}
```

Groups are there, but the properties (`topic`, `pollIntervalMs`, …) are
**zero**. The KDoc descriptions have nothing to attach to: in the metadata model,
`description` lives on a `property`, and not a single `property` was generated.

### KDoc is alive and well

The first suspicion is that kapt strips comments when generating stubs. Let's
check the stub itself (`build/tmp/kapt3/stubs/.../OutboxProperties.java`):

```java
public final class OutboxProperties {

    /**
     * Kafka topic events are published to. Required.
     */
    @org.jetbrains.annotations.NotNull()
    private final java.lang.String topic = null;

    /**
     * Kafka topic events are published to. Required.
     */
    @org.jetbrains.annotations.NotNull()
    public final java.lang.String getTopic() {
        return null;
    }
    // … same for every other field and getter
}
```

The KDoc is intact — on fields and on getters, as proper Javadoc. So the missing
descriptions are **not** a KDoc problem: the moment properties start being
generated, descriptions will follow. The real issue is that no properties are
generated at all.

### Root cause: immutable constructor + two constructors in the stub

The same stub reveals the key detail — the class has **two** constructors:

```java
// 1) the full one, with all parameters
public OutboxProperties(java.lang.String topic, long pollIntervalMs,
                        int batchSize, int maxAttempts, Liquibase liquibase) {
    super();
}

// 2) a synthetic no-arg one — Kotlin generates it because EVERY parameter
//    has a default value
public OutboxProperties() {
    super();
}
```

From here, the Spring Boot processor's own logic kicks in. For a type it picks
one of two binding modes:

- **constructor binding** — one property per constructor parameter (for
  immutable classes);
- **JavaBean binding** — one property per getter/setter pair.

Constructor binding is chosen when there is exactly one constructor, or when the
intended one is annotated with `@ConstructorBinding`. Here there are **two**
constructors and neither is annotated → the processor falls back to JavaBean
binding. And in JavaBean mode a property needs a **setter**. `val` fields have no
setters → zero getter/setter pairs → `properties: []`.

So the fatal combination is an immutable `data class` whose parameters all have
defaults — and it is precisely those defaults that conjure the second, no-arg
constructor.

### `@ConstructorBinding` does not save it

The obvious move is to annotate the primary constructor to force constructor
binding:

```kotlin
data class OutboxProperties @ConstructorBinding constructor(
    val topic: String = "",
    // …
)
```

The annotation lands where it should in the stub:

```java
@org.springframework.boot.context.properties.bind.ConstructorBinding()
public OutboxProperties(java.lang.String topic, long pollIntervalMs, …) { super(); }
```

But the result is **worse**: `properties` is still empty, and on top of that the
nested `dema.outbox.liquibase` group disappears. On this toolchain (Kotlin 2.2 +
Spring Boot 3.4.9) the annotation does not solve the problem.

## The fix

The working path is to hand the processor a **JavaBean binding**: make the
properties mutable (`var`) so setters exist. I verified two shapes; both produce
the full result:

- a plain `class { var … }`;
- a `data class(var …)` — which keeps the named-argument constructor, so existing
  call sites (`OutboxProperties(topic = …, …)`) and tests keep compiling. I kept
  this form.

```kotlin
@ConfigurationProperties("dema.outbox")
data class OutboxProperties(
    /** Kafka topic events are published to. Required. */
    var topic: String = "",
    /** Scheduler poll interval (ms). */
    var pollIntervalMs: Long = 1000,
    /** Rows fetched per poll. */
    var batchSize: Int = 100,
    /** Event becomes dead (excluded from fetch) after this many failed sends. */
    var maxAttempts: Int = 5,
    var liquibase: Liquibase = Liquibase(),
) {
    data class Liquibase(
        /** Auto-create the outbox_events table on startup. */
        var enabled: Boolean = true,
    )
}
```

Rebuild, and the metadata is complete, with descriptions straight from the KDoc:

```json
{
  "properties": [
    { "name": "dema.outbox.batch-size", "type": "java.lang.Integer",
      "description": "Rows fetched per poll.",
      "sourceType": "org.dema.outbox.OutboxProperties" },
    { "name": "dema.outbox.liquibase.enabled", "type": "java.lang.Boolean",
      "description": "Auto-create the outbox_events table on startup.",
      "sourceType": "org.dema.outbox.OutboxProperties$Liquibase" },
    { "name": "dema.outbox.max-attempts", "type": "java.lang.Integer",
      "description": "Event becomes dead (excluded from fetch) after this many failed sends.",
      "sourceType": "org.dema.outbox.OutboxProperties" },
    { "name": "dema.outbox.poll-interval-ms", "type": "java.lang.Long",
      "description": "Scheduler poll interval (ms).",
      "sourceType": "org.dema.outbox.OutboxProperties" },
    { "name": "dema.outbox.topic", "type": "java.lang.String",
      "description": "Kafka topic events are published to. Required.",
      "sourceType": "org.dema.outbox.OutboxProperties" }
  ]
}
```

All five properties, each with its `description` from KDoc. IntelliJ now gives
both completion under `dema.outbox.*` and doc tooltips.

## Does it work on Spring Boot 3.5+?

A separate question: does the fix carry over to Spring Boot 3.5 unchanged, and
does 3.5 happen to fix the immutable case? I checked by temporarily pinning the
processor version (the BOM stays on 3.4.9) and confirmed it really resolved to
3.5.0:

```
\--- org.springframework.boot:spring-boot-configuration-processor:3.4.9 -> 3.5.0 (c)
```

Results:

- **The fix (`data class(var …)`) on processor 3.5.0** — works unchanged: the
  same five properties with KDoc descriptions.
- **Immutable `data class(val …)` on processor 3.5.0** — still only `groups`,
  zero `properties`.

So **upgrading Spring Boot to 3.5 does not fix the immutable case by itself** —
the JavaBean (`var`) form is still required on both 3.4.9 and 3.5.0. The proposed
fix, on the other hand, is compatible with 3.5 as-is.

> Caveat: what I tested was metadata generation under processor 3.5.0 (one patch
> of the 3.5 line), not a full runtime upgrade of the whole BOM.

## Experiment matrix

| Class shape                                   | Processor 3.4.9              | Processor 3.5.0              |
| --------------------------------------------- | --------------------------- | --------------------------- |
| `data class(val …)` (immutable)               | groups, **0** properties    | groups, **0** properties    |
| `data class(val …)` + `@ConstructorBinding`   | **0** properties, nested group lost | —                   |
| `data class(var …)` (chosen fix)              | **5** properties + KDoc     | **5** properties + KDoc     |
| `class { var … }` (plain JavaBean)            | **5** properties + KDoc     | — ¹                         |

¹ Not run separately; same JavaBean binding path as the `data class(var …)` form
verified on 3.5.0.

## Details and gotchas

- **`annotationProcessor` ≠ `kapt`.** For Kotlin the processor must live in the
  `kapt` configuration, otherwise it never touches your Kotlin classes.
- **kapt keeps KDoc.** Descriptions go missing not because of the stubs, but
  because no `property` is generated for an immutable class in the first place.
- **`groups` ≠ `properties`.** A group comes from the `@ConfigurationProperties`
  annotation itself and shows up even when no property is generated. "Group
  present, properties empty" is the tell-tale sign of a binding problem, not a
  wiring one.
- **`defaultValue` is not emitted**, even with `var` — a known limitation of the
  processor's Kotlin support (see spring-boot#15397). Not critical for completion
  and tooltips; the descriptions are what matter here.
- **Names are kebab-cased** (`pollIntervalMs` → `dema.outbox.poll-interval-ms`),
  nested objects add a prefix (`dema.outbox.liquibase.enabled`).
- **Cost of `val` → `var`:** the properties become mutable. For configuration
  that is bound once at startup this is just Spring's standard JavaBean mode, so
  the practical risk is nil. If immutability is non-negotiable, the alternative is
  to maintain `META-INF/additional-spring-configuration-metadata.json` by hand
  (duplicating descriptions, which defeats the point of KDoc).

## The patch

`build.gradle.kts`:

```diff
 description = "Transactional outbox starter (Postgres + Kafka)"

+plugins {
+    kotlin("kapt")
+}
+
 dependencies {
     api("org.springframework.boot:spring-boot-starter-jdbc")
     api("org.springframework.kafka:spring-kafka")
     api("org.liquibase:liquibase-core")

     implementation(libs.kotlin.logging)
     implementation("org.springframework.boot:spring-boot-autoconfigure")
     implementation("com.fasterxml.jackson.module:jackson-module-kotlin")
+
+    kapt("org.springframework.boot:spring-boot-configuration-processor")
```

`OutboxProperties.kt` — six `val` → `var` (the `data class` form is kept, so the
constructor and call sites stay untouched).

## Takeaways

1. No metadata for a Kotlin `@ConfigurationProperties`? First check that the
   processor is wired through **kapt**, not `annotationProcessor`.
2. File exists but holds only `groups` with an empty `properties`? That is an
   immutable `data class` with `val`. Switch the properties to `var` (JavaBean
   binding) and the KDoc descriptions flow into the metadata on their own.
3. Upgrading to Spring Boot 3.5 does not remove that second trap — `var` is
   needed either way, but the fix is compatible with 3.5 without changes.
